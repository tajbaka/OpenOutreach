1. LINKEDIN DAEMON  (manage.py with no arguments)
================================================================================
The long-running daemon owns browser-backed LinkedIn task execution. Active
hours, rest days, feature flags, and per-profile limits gate its work.

CONNECT
  - Sends a connection request/note when enabled.
  - Persists successful outbound activity to crm.Message.

SWEEP_CONNECTIONS
  - Detects accepted invitations in bulk.
  - Advances per-Lead/per-Campaign Deal automation state.
  - Captures the conversation snapshot and persists crm.Message rows.

FOLLOW_UP / GMAIL SEQUENCE
  - Outbound automation lanes remain separately feature-gated.
  - They are not invoked by refresh_crm, sync_sheets, generate_followups, or
    any data-ingestion runbook.

Deal is an outreach-delivery state machine. Deal.state=COMPLETED means the
automation lane finished; it never means the account Opportunity is Closed Won.


================================================================================
2. CONTEXT INGESTION
================================================================================
crm.Message is the canonical stored LinkedIn/Gmail communication timeline.
crm.Meeting and crm.MeetingNote store meeting facts and note context.

Populated by:
  - daemon/realtime/sweep paths for LinkedIn events;
  - manage.py backfill_messages for later LinkedIn thread activity;
  - manage.py sync_gmail_context for Gmail threads and Gmail-delivered
    Gemini/Meet notes;
  - the connector workflow in docs/data-sync-workflow.md for Calendar and
    Drive-only Gemini context; and
  - refresh_crm's incremental Granola batch sync.

Important freshness boundary:
  - refresh_crm does not log into LinkedIn;
  - refresh_crm does not query Google Calendar or Drive directly;
  - a successful refresh processes stored context safely but cannot certify
    those separate inputs are fresh.

Keep backfill_messages scheduled and run Calendar/Drive ingestion after
important meetings when those sources are needed.

3. CANONICAL SALES CRM IN POSTGRES
================================================================================
Lead / Deal remain contact and outreach-automation records.

The sales operating model is separate:
  Account
    -> Opportunity (owner, stage, 15-step motion, commercial state)
      -> OpportunityContact (champion / decision maker / stakeholder / other)
      -> OpportunityAction (one current open/waiting Action)
      -> OpportunityStageEvent (audit history)
      -> OpportunitySheetState (three-way merge baseline)

Macro-stage mapping:
  Prospecting 1
  Discovery 2
  Demo Planning 3-4
  Evaluation 5-6
  Sandbox/Pilot 7-10
  Commercial 11
  Procurement/Legal 12-14
  Closed Won
  Expansion 15
  Closed Lost

Explicit Opportunity owner is authoritative. Sender inference is fallback-only
and must be unambiguous.


================================================================================
4. CANONICAL CRM REFRESH  (manage.py refresh_crm)
================================================================================
Default invocation is an exact no-persistent-write dry-run:

  .venv/bin/python manage.py refresh_crm

Apply only after reviewing the report:

  .venv/bin/python manage.py refresh_crm --apply

One run:
  1. acquires the nonblocking CRM lock;
  2. verifies/inventories GOOGLE_SHEETS_ID and rejects the separate Sales
     Motion workbook;
  3. refreshes Gmail/Gemini context and batch-syncs Granola unless skipped;
  4. reads human-owned Sheet edits and imports valid changes by stable ID;
  5. bootstraps conservative Opportunities and recalculates Actions through
     the shared time-aware policy;
  6. incrementally publishes People and asserts preservation invariants;
  7. incrementally publishes Opportunities;
  8. regenerates managed Pipeline, Recovery, and owner Followups ranges; and
  9. records exact WorkflowRun telemetry.

One-time legacy Followups migration:
  - imports human state only when stable evidence identifies one canonical row;
  - never guesses an unresolved material row;
  - preserves every untouched old sender tab under a dated Legacy title;
  - reports unresolved rows for human review without blocking otherwise-safe
    canonical activation; and
  - prepares and validates all affected sender replacements before one atomic
    title batch activates them. A pre-swap failure leaves all old canonical
    titles active.

Granola is primary meeting context; stored Gemini is secondary. Context cannot
create eligibility.

Action aging:
  - 0-21 days: daily only when work is genuinely required;
  - 22-60 days: Recovery, absent an explicit current-action exception;
  - over 60 days: archive/nurture, under the same exceptions.

Future Waiting Actions disappear until due. Closed, Don't Send, disqualified,
non-actionable failed, and polite-decline records stay out of daily queues.


================================================================================
5. GOOGLE SHEETS SURFACES
================================================================================
People
  - Durable growing contact ledger.
  - Updated in place/appended; never clear/rebuild/reorder/prune.
  - Stable Lead ID plus canonical LinkedIn URL.
  - Human/unknown cells, formulas, comments, and formatting are preserved.

Opportunities
  - Durable editable canonical table.
  - Human fields merge Sheet -> DB before system fields publish DB -> Sheet.
  - Conflicts/invalid edits fail closed rather than being guessed.

Pipeline
  - Derived from Opportunity.stage only.
  - Visual card position is never imported as stage.

<Owner> - Followups
  - Derived due-now Actions keyed by Action, Opportunity, and Lead IDs.
  - Imports Handled, Disposition, Draft, Channel, Waiting, and Manual pin before
    regeneration.
  - One Action appears under at most one explicit owner.
  - Dated Legacy tabs are frozen first-run evidence/recovery copies, not queues
    to merge by name or schedule for sending.

Recovery
  - Derived older-inactive/unassigned review surface, separate from daily work.

ICP Goals / separate Sales Motion workbook
  - Read-only inputs to this workflow.


================================================================================
6. NARROW PUBLISHER AND MANUAL DRAFTING
================================================================================
manage.py sync_sheets
  - Narrow People planner/publisher only.
  - Does not run LLM synthesis, assign opportunity stages, choose followups,
    publish Pipeline, or rebuild sender tabs.

manage.py generate_followups
  - Exports explicitly owned canonical daily Actions for draft generation.
  - Validates draft decisions by stable IDs and context fingerprint.
  - Stores/publishes drafts but never sends them.
  - The retired name-based rebuild requires explicit --legacy and is never a
    scheduled production path.

Operators review and send messages manually, then record human action state in
the stable-ID Followups row.

8. ONE-OFF CONNECTION IMPORT
================================================================================
  .venv/bin/python manage.py import_connections --csv <file> [--campaign N]

The command uses BACKFILL_LINKEDIN_USERNAME/PASSWORD, imports only matched
accepted connections, persists message history, and never writes Sheets
directly. The next CRM refresh appends eligible contacts to People and
conservatively evaluates whether an Opportunity should exist.
