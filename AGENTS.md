# AGENTS.md

## Rules

- **Python env**: Always use `.venv/bin/python` (not system `python3`).
- **Commits**: No `Co-Authored-By` lines. Single-line messages (no body).
- **Dependencies**: Managed in `requirements/*.txt` (used by local dev and Docker).
- **Docs sync**: When modifying code, update AGENTS.md and ARCHITECTURE.md to reflect changes.
- **No memory**: Never use the auto-memory system (no MEMORY.md, no memory files). All persistent context belongs in AGENTS.md or ARCHITECTURE.md.
- **Error handling**: App should crash on unexpected errors. `try/except` only for expected, recoverable errors. Custom exceptions in `exceptions.py`.
- **No general backward compat**: CRM models are owned by this project, so do not add broad compatibility shims or re-export modules. `refresh_crm_v2` is the canonical publisher. Its one-time cutover may import only exact stable-ID human state from legacy tabs, never guess unresolved rows, stages both v2 surfaces before one atomic title swap, and compensates the title swap if the outer DB transaction rolls back. `refresh_crm` is retired and must fail closed once `Active Accounts` or `Actions` exists; do not route production work back through it.
- **Sales copy skills**: `skills/boundera-sales/` is only for one-off Boundera email, LinkedIn, SMS/Slack, recap, scheduling, and objection wording outside the structured campaign Sheet. `skills/boundera-icp-messages/` exclusively authors or reviews the shared `General ICP Messages` Google Sheet. Its exact eight columns show one complete ICP sequence left-to-right. The skill reads its concise human-maintained persona angles, the live general draft, the latest explicitly imported JSON when available, shared 20x/Rev5 references, and measurable channel budgets. Operator-only per-cell review state lives in `linkedin/general_icp_review_status.json`, keyed by exact ICP label and protected by the live cell hash; the skill must inspect it at the start of every General ICP task and update every touched field immediately after an authorized Sheet edit and successful readback. Runtime and Sheet-to-campaign import code never read it. Neither skill keeps a static product-capability inventory: named capabilities such as VDR, trust centers, SDRs, schemas, connectors, KSI evaluation, or assessor workflows require targeted verification in the current FedRampGPT documentation, implementation, and tests, while campaign copy proves only configured messaging. The Sheet skill never imports, sends, or activates a campaign unless the user separately requests the appropriate safe command. Neither copy skill loads the sales-motion video framework.
- **Versioned campaign messages**: `General ICP Messages` is mutable authoring state with the exact eight-column wide schema in `linkedin/general_icp_messages.py`. `ICP` must encode `Role | Company Size | FedRAMP Stage | Revenue Intent`, where Revenue Intent is exactly `Direct agency`, `CSP ecosystem`, `Both`, or `Unclear`; the explicit importer derives the fixed FedRAMP Marketplace CSP program identity, stable intent-specific audience key, role persona, and segment from that manually authored label. `Lead.role_tag` is independent operator-reviewed classification metadata and is not used to construct or select an ICP audience automatically. Runtime code never reads the Sheet. `sync_general_icp_messages` previews by default and only `--apply` imports the validated draft into `shared_programs` in the existing `linkedin/icp_messages.json` and `gmail/icp_emails.json` v2 envelopes. `publish_general_icp_messages` reads only those checked-in JSON stores. `import_campaign` may accept `message_program_key`; campaign creation snapshots the current matching JSON program into an immutable `MessageProgramVersion` and assigns it to `Campaign.active_message_version`. `CampaignMessageEnrollment` then freezes one Deal's version, canonical audience, and operator; `OutboundDelivery` freezes rendered subject/body/media before a Task can execute. A bound Deal must fail closed on missing or mismatched delivery identity and may never reread JSON or mutable Sheet copy. Transitional sender-specific content lives under `sender_icps`; hidden sender tabs and `sync_icp_messages` remain only the unbound-campaign rollback path.
- **Consolidated ICP authoring**: The General draft was physically consolidated on 2026-09-07 to 37 rows: Business leaders (13), Technical (13), and FedRAMP-adjacent (11), using `Any Size` while preserving existing stage and revenue-intent combinations. Do not regenerate the old role/size rows by default. Blank conflicting sequence fields remain unfinished, not approved omissions. This is Sheet authoring state only, not automatic lead routing, a JSON import, or a campaign change.
- **Sales conversation reference**: Before preparing a call, discovery questions, stakeholder strategy, deal inspection, or next-step recommendation, read `docs/sales-motion-summary.md`, identify the opportunity's current step from evidence, and ask only questions appropriate to that step. Use `docs/sales-motion-framework.md` when exact task IDs or operating guidance matter, and `docs/sales-motion-video-transcript.md` when source timing or rationale matters. Do not use these references for copy-only drafting. Do not conflate champion, end user, evaluator, sponsor, approver, and authorized signatory or pull later-stage approval questions into an early demo.
- **Arian calendar links**: Use the canonical constants in `linkedin/calendar_links.py`, not remembered or inline Cal.com URLs. Run its helper from the repo root with `.venv/bin/python skills/boundera-sales-motion/scripts/clone_sales_motion.py`; credentials stay in ignored `secrets/sheets-service-account.json`. Only an attributed human inbound LinkedIn/Gmail `Message` for that exact sender removes a row. Preserve all DB history, People, campaign state, and delivery schedules. This view is not an outreach queue or proof of exact acceptance time. `sync_accepted_connections` previews by default; `--apply` refreshes only this owned tab. Unexpected schemas/formulas/chips/populated extra columns fail closed; native readback is mandatory. No migration is needed.

`import_connections` reads a CSV with either of these header sets:
- `LinkedIn URL, First Name, Message` (manual outreach log; `Message` becomes the seeded outbound `crm.Message`)
- `Profile URL, First Name, Last Name, Company` (standard LinkedIn-Connections export; no outbound message column)

The parser auto-detects which format and treats `Message` / `Last Name` / `Company` as optional bonuses. It logs into LinkedIn using `BACKFILL_LINKEDIN_USERNAME`/`BACKFILL_LINKEDIN_PASSWORD` from `.env`, scrapes the Connections page back N days, and creates Lead+Deal rows at `state=CONNECTED` for each row also present in the scraped connections. The SKIP path (lead already at CONNECTED+) backfills `Deal.connected_at` from the scrape's `connected_on` date if it was null. Skips URLs that already have a Deal in any non-backfill campaign so the daemon's outreach state is never disturbed. Outbound messages from the CSV are persisted to `crm.Message` with `external_id="csv:<path>:<url>"`; inbound messages flow through `get_conversation`'s persist hook. `sync_sheets` mirrors these to Google Sheets on its next hourly run — this command never touches Sheets directly.

`discover_inbox_leads` crawls LinkedIn Messaging conversations via the Voyager Messaging inbox API, not the Connections page. After login it first opens the visible browser tab to `/messaging/` and pauses briefly, then reads the same authenticated Messaging GraphQL endpoints from that browser context. The first inbox batch uses LinkedIn's recent-conversation query; older batches use the same `lastUpdatedBefore` / `nextCursor` category query the UI emits when the conversation list is scrolled, stopping at `--since-days` (default 90) or `--max-pages`. It skips existing CRM Leads by canonical LinkedIn URL, `Lead.public_identifier`, stored profile URN, and any thread already present in `crm.Message.thread_external_id`. It resolves/enriches the other 1:1 participant profile when LinkedIn allows it; if Voyager blocks the full profile, it falls back to the inbox participant payload (name, headline, profile URL / `fsd_profile` URN) so private/restricted inbox senders can still be reviewed without breaking duplicate checks. It fetches the thread, then asks a Boundera FedRAMP/CMMC LLM prompt (`inbox_lead_relevance.j2`, using `LLM_API_KEY` / `AI_MODEL`) whether the profile plus conversation is relevant and which canonical `Lead.icp` bucket it belongs to (`CSPs`, `3PAOs/Assessors`, `Advisors`, `Channel`, `CMMC Buyers`, `CMMC Advisor/Channel`). The selected Campaign is only the destination Deal campaign; stale Campaign objective/docs are not used for inbox discovery relevance. With `--apply`, qualified discoveries are inserted as `Lead` plus `Deal(state=CONNECTED)`, `Lead.icp` is stamped from the classifier, and their thread is persisted through `linkedin.db.messages.persist_thread`; `Deal.last_reply_at` is stamped from the newest inbound message. Because it creates Deals at `CONNECTED` and leaves `Lead.disqualified=False`, `sync_sheets` will mirror them to the People tab on the next run. It never creates `Task` rows, so follow-up automation only sees these records if a separate workflow later chooses to act on them.

## Architecture (quick reference)

- **Explicit ICP import and storage**: `Lead.icp` allows 160 characters (migration `crm.0022_lead_icp_audience_length`), matching the frozen audience-key limit without changing existing classifications or `role_tag`. CSV seed import validates shared audience keys once against explicitly imported JSON and preserves exact keys; existing legacy aliases still normalize. Unknown nonblank selections fail instead of silently becoming blank. Bound enrollment locks only the Campaign row when selecting its nullable active-version join, keeping PostgreSQL locking valid. Migration execution must remain separate from live worker activation; QA applies migrations only to its disposable database.

- **Isolated campaign QA**: `scripts/qa_campaigns.py` launches `tests/campaign_qa/` with a sanitized environment, dotenv loading disabled, private-data reads/browser subprocesses/network blocked, and libpq restricted to the runner-owned PostgreSQL 17 Unix socket. Each run migrates a fresh synthetic test database and removes it only after verifying shutdown. It reads imported `shared_programs` without modifying JSON, Sheets, review state, or production data. Reports include actual-copy previews, scenario expected/actual results, failures, input hashes, and cleanup status under ignored `artifacts/qa/campaigns/<run>/`. Fixture-only rendering is explicitly separate from real enrollment/handler tests; an upstream failure must not be reported as downstream coverage. This harness has no live mode and does not replace a human-run provider/UI smoke test.

- **Incomplete sequence safety**: Automatic version-bound LinkedIn follow-up startup queues nothing if the channel is absent or its first message (step 0) is missing; a later message does not authorize skipping the unfinished first copy. A configured missing-first sequence emits a warning and appears as a copy hold in campaign QA, not as a completed sequence. An absent Gmail channel is a normal no-op; configured Gmail sequences retain their existing first-effective-step semantics. Neither case consults fallback copy or alters the imported JSON.

- **Meeting context**: `linkedin/granola.py` is the read-only bearer-authenticated client; `linkedin/granola_sync.py` batch-refreshes/cache-matches notes with bounded retries, pacing, watermarks, and exact attendee email → exact attendee identity → exact event/account+time+title matching. Loose transcript/body matching is prohibited. Cached Granola is primary and stored Gemini (`MeetingNote` or live `Meeting.gemini_notes_raw`) is secondary. Context never widens action eligibility. `manage.py granola_notes` remains the standalone read-only lookup command; scheduled persistent sync/rematch runs through `sync_crm_v2_context --apply` before publication.
- **Feed engagement Slack lanes**: High-signal feed alerts render the post date first, the author in a Slack header, the post body, existing analysis context, then `Open post`, `Post context`, `Like`, and `Comment on LinkedIn` in one action row. The existing `/api/slack_enrich` endpoint only merges each feed module's intent registry and delegates to it. `api/slack_feed_context.py` owns the read-only Post context modal: the complete saved post is rendered first across as many Slack-safe blocks as needed, followed by author, analysis, timestamps, sightings, and a modal-only `Generate AI summary` action. Generated post summaries are transient and use the existing Vercel LLM configuration. `api/slack_feed_like.py` owns a compact sender confirmation modal and raw-SQL enqueue for an independent sender-scoped `feed_like` task. The matching main daemon runs the existing live reaction-state checker outside active-hour gating: `no reaction` is clicked, an existing Like succeeds without a click, and another reaction is preserved. Like status has its own pure block renderer and never replaces feed-comment status. `api/slack_feed_comment.py` remains responsible only for sender selection, public-comment AI drafting, raw-SQL enqueue/cancel, and comment modal UI. Queueing a comment closes the modal and edits the original alert in place, retaining every source block while inserting one inline queued status with `Cancel queued comment`. Shared compressed source-block transport lives in `api/slack_feed_common.py`. Comment submit creates a sender-scoped `feed_comment` task and `LinkedInFeedComment` ledger. The matching main daemon runs the exact-post Playwright UI action outside normal active-hour gating, with no Voyager fallback, then replaces the inline status on the original alert with the sent/failed/uncertain outcome and removes the cancel control. `linkedin/feed_slack_status.py` is the pure comment-status renderer; feed engagement status paths never create Slack thread replies. After typing, submit discovery polls six nearby composer ancestors for explicit controls plus text-only `Post`/`Comment` variants; this reaches LinkedIn's deeply nested current Comment submit while excluding post-level controls outside the composer boundary. A submit is verified only when the draft appears inside a rendered LinkedIn comment item, including the current signed-in renderer's `replaceableComment_urn:li:comment` component; composer text never counts as sent. Chuka is displayed as Eddy in Slack but remains canonical in payloads. The ledger is stamped immediately before submit; retries after sent/uncertain or a recovered submit attempt fail closed. Long generated comments retain the shared human typing cadence while deriving the Playwright timeout from text length. `run_feed_comment_once --handle <django-username>` is the bounded live-QA runner: it verifies the authenticated identity and claims exactly one matching feed-comment task without touching other daemon lanes. No new endpoint, Slack app, or env vars are required beyond the existing Vercel Slack/DB/LLM configuration.
- **Feed comment Slack diagnostics**: Queue, cancel, and daemon outcome states explicitly update the original alert. The interaction `response_url` is preferred and `chat.update` is the fallback; failures are logged without creating a thread reply or blocking approved LinkedIn work.
- **Feed comment cancellation window**: Newly submitted feed-comment tasks are scheduled 60 seconds in the future so the operator has a real pending-only cancellation window before a daemon can claim the task.
- **Feed comment auto-like**: Every approved feed-comment task first runs the isolated `linkedin/actions/feed_like.py` action on the exact post. Reaction-control discovery polls for delayed LinkedIn rendering, accepts both `Reaction button state` and state-bearing `aria-pressed` markup, and excludes comment-level Like controls. Live ARIA state remains authoritative: `no reaction` is clicked and verified as `Like`, an existing `Like` is left untouched, any other reaction is preserved, and ambiguous controls fail closed. Like failures are reported in the final Slack comment status but fail open so they never block the approved comment.

For detailed module docs, see `ARCHITECTURE.md`.

- **Entry**: `daemon_supervisor.py` is the canonical normal runtime: `make run`, `make run-awake`, the Windows awake launcher, and the Docker start script use it to supervise one browser-backed `manage.py` LinkedIn child plus the mapped independent Gmail worker. Terminal runs retain Git polling/auto-update; immutable Docker startup passes `--no-update`. `make run-linkedin` / no-argument `manage.py` is the explicit LinkedIn-only diagnostic and supervisor child path. The no-argument `manage.py` child runs startup checks → onboarding → browser → task queue loop and auto-migrates + bootstraps CRM; with arguments it delegates to Django CLI. Startup integrity checks run first in an unsupervised no-args child, before migrations: `linkedin/version_check.py:check_for_updates()` compares the checkout against its git upstream (`@{u}`) and, when behind, prompts on a TTY or auto-pulls headless. A successful `git pull --ff-only` exits 0 so the process can restart on fresh code; a failed pull exits 1 after `notify_error`. The supervisor marks its child so this nested update check is skipped. `linkedin/env_check.py:check_env_vars()` logs one grouped advisory warning for missing env vars declared in `linkedin/env_spec.py`, which is the canonical env-var registry.
- **State machine**: `enums.py:ProfileState` — QUALIFIED → READY_TO_CONNECT → PENDING → CONNECTED → COMPLETED / FAILED. Deal.state is a CharField with ProfileState choices (no Stage model). `ClosingReason` (COMPLETED/FAILED/DISQUALIFIED) on Deal.closing_reason. `Lead.disqualified=True` = permanent exclusion. LLM rejections = FAILED Deals with DISQUALIFIED closing reason (campaign-scoped). `Deal.connected_at` is stamped once when `set_profile_state` flips into CONNECTED — stable timestamp the daemon's rigid follow-up handler (`linkedin/tasks/follow_up.py`) uses for connected-no-reply cohort tracking.
- **LinkedIn message media**: Only current post-connection `follow_up` and `drip_linkedin` deliveries may carry media. Each message permits at most one reviewed `.gif` or `.mp4` under `assets/follow_up/`; `linkedin/message_media.py` rejects traversal/escape, missing or empty files, unsupported extensions, invalid GIF/MP4 signatures, and files over 20 MiB, then computes the MIME type, size, and SHA-256 identity. Connection-request notes, Gmail, native LinkedIn voice notes, and the Voyager media-upload API are outside this path. Media sends use `send_direct_message_once()` through one exact-member-URN compose route: attach and poll upload readiness, type the body, run the caller's final persisted stop callback after upload and immediately before submission, then perform one Send click with no popup or API fallback. The current `FOLLOW_UP` media branch retains current ownership/state/campaign/stop semantics: a definite pre-submit technical failure may use its existing 24-hour retry, a final-guard block does not retry, and an ambiguous post-click result raises `LinkedInMessageSubmissionUnclearError` so the Task fails without advancing or resending. Confirmed current sends persist validated media evidence in `crm.Message.raw`. Drip manifest schema v2 freezes media type/reference/MIME/size/SHA-256 into both the immutable version and `DripDelivery`; execution revalidates those bytes, pauses the lane on missing/invalid/drifted media, preserves the existing attempt boundary for unclear results, and records the same evidence in `crm.Message.raw`.
- **Current LinkedIn media crash recovery**: `linkedin/tasks/follow_up_submission.py` locks the Lead, reruns the final guard, and stamps the exact current `follow_up` Task payload immediately before the sole Send click, serializing same-operator sibling campaign Tasks. A LinkedIn-confirmed send must then have its exact media-bearing `crm.Message` re-read successfully before any action/state/successor advancement. Startup recovery requeues a stale running or post-confirmation failed marked Task only when that exact evidence exists, preserves its marker and sequence payload through follow-up catch-up, and lets sent-step dedupe heal the successor; a marked Task without evidence becomes failed/unclear and blocks same-operator catch-up plus already-pending sibling handlers for that Lead, without blocking another operator. Ordinary pre-submit stale Tasks retain normal recovery.
- **Drip campaigns**: `drip/` is an independent, versioned theme-campaign domain layered onto the existing Task infrastructure; it does not reuse current `FOLLOW_UP`/`GMAIL_FOLLOW_UP` lifecycle state and never changes `Deal.state`. One reviewed manifest contains ICP themes plus sender-specific LinkedIn/Gmail renditions. An enrollment freezes its campaign version, ICP, canonical operator, provider account, sender identity, and recipient identity, and owns independent LinkedIn/Gmail lanes. A configured LinkedIn lane is reviewable only when the Lead URL, `public_identifier`, embedded profile URL/public identifier, and exact `urn:li:fsd_profile:...` agree and that URN is not stored on another Lead; the canonical URL and member URN are frozen on the lane and revalidated at apply, reservation, and the pre-click boundary. Sender ownership requires an exact invitation ledger or exact Deal-bound outbound Message and never follows Campaign ownership alone. Current outreach hands off each channel only after exact persisted completion evidence (or a human-reviewed true `not_applicable` decision); a current Gmail Task or LinkedIn media Task that crossed its durable submission boundary without exact persisted outbound evidence blocks both handoff and `not_applicable` review for that channel/operator. Lead-row locking plus `drip_owns_channel()` prevents current enqueue/heal/handler paths from taking a handed-off channel back. Reviewed enrollment scopes its PostgreSQL row lock to the `DripCampaign` row while selecting the nullable active version, so the outer join remains valid. `reconcile_drips` is finite and database-only: dry-run is the default, `--apply` records handoff/progress and creates at most one frozen outstanding delivery/Task per lane, and Gmail timing stays channel-local. LinkedIn reconciliation computes one deterministic absolute due time from the later of the channel minimum and the pass snapshot, then moves it only forward into active hours/rest days; it never records a due time earlier than the applicable channel anchor plus the manifest delay. A persisted inbound LinkedIn or Gmail `crm.Message`, qualifying persisted Meeting, disqualification, or suppression stops both lanes through the shared DB-local policy; no provider refresh happens inside the stop check or immediately before normal send. `drip_linkedin` is consumed by the matching existing sender daemon below current connect/follow-up work and uses one direct-message UI route addressed only by the reviewed frozen member URN; it never resolves a mutable Lead at send time, and a post-click ambiguous result becomes `unclear` and is never auto-rerouted. `drip_gmail` is consumed by the independently supervised account-scoped Gmail worker and continues the exact inherited sender-mailbox Gmail thread or opens a reviewed new thread. Current outbound enqueue and executor paths require their exact Campaign/Deal Campaign to remain active, so a late acceptance can reconcile a finished historical Deal to `CONNECTED` without resurrecting its LinkedIn/Gmail sequence. The one-time `retire_legacy_outbound` cutover is review-artifact gated, process-quiesced, table-locked, exact-state checked, and preserves historical rows while creating empty active runtime Campaign anchors for Arian/Chuka. Campaign/enrollment controls and Admin are implemented, and a controlled internal two-theme provider QA completed, but no production manifest/cohort is published or enrolled and no reconciler schedule is installed.
- **Task queue**: `Task` model (persistent). Types include `connect`, `follow_up`, `drip_linkedin`, `drip_gmail`, `sweep_connections`, `discovery`, `status_summary`, `enrich_phone`, `enrich_email`, `gmail_follow_up`, `manual_reply`, `feed_comment`, and `feed_like`. Handlers in `linkedin/tasks/` use `handle_*(task, session, qualifiers)` for current LinkedIn/browser work; drip executors live in `drip/tasks/`, and current Gmail cadence code lives in the top-level `gmail` package. `Task.objects.claim_next()` atomically flips the returned task from `pending` to `running`; this is part of the cancel-safety contract for manual replies, so callers must treat a returned task as already claimed. Claim priority is manual reply → feed comment → feed Like → maintenance sweep overdue beyond `CONNECTION_SWEEP_MAX_QUEUE_DELAY_MINUTES` → status summary → due current follow-up/connect delivery → other maintenance (including `drip_linkedin`) → normal sweep. This keeps current delivery work ahead of drip and routine maintenance while giving the now-bounded sweep deterministic fairness. Startup recovery is sender-scoped and age-gated by `TASK_RUNNING_STALE_MINUTES`; drip recovery also consults its attempt ledger so a known pre-submit failure can retry while a possibly submitted attempt becomes `unclear`. One daemon restart must never reset another sender's running browser task. `manual_reply` is the Slack-to-LinkedIn reply lane: Slack modal submit inserts a pending task with `lead_id`, `operator`, `message`, and Slack message metadata; the queued Slack status includes a cancel button that deletes the task only while it is still `pending`. The daemon claims matching-operator manual replies ahead of normal outbound work, sends them through the same logged-in Playwright page, bypasses active-hours sleeps when due, and leaves quotas, sequences, and Deal state untouched. If best-effort context/preview fetch fails, the reply modal still opens. Email enrichment is **not** Slack-triggered: when post-accept Gmail is enabled, post-accept Gmail scheduling queues `enrich_email` for leads without `Lead.email`. `enrich_email` uses BetterContact in email-only mode (`enrich_email_address=true`, `enrich_phone_number=false`), writes found addresses to `Lead.email`, records definitive BetterContact answers in `Lead.email_providers_tried`, and then queues `gmail_follow_up` step 0. The function uses raw `psycopg` (no Django import), and `SLACK_BOT_TOKEN` is required for `views.open`/`views.update`; queued status updates prefer the interaction `response_url` and only fall back to `chat.update` when metadata is available, while sent/failed status uses daemon-side `chat.update` and falls back to `response_url`. The `Task` table is the entire contract between the function and the daemon. The function re-posts the notification with the **select menu kept live** (`render_response_blocks`) so the operator can run several providers on one lead from the same message; a status line accumulates the requested providers (its `block_id` carries the set across picks). The realtime listener can *also* auto-enqueue a `waterfall` task on every inbound reply, gated by `ENABLE_AUTO_PHONE_ENRICHMENT` (default off). Phone enrichment paths dedup per `(lead, provider)` against an existing pending/running task — so BetterContact and LeadMagic can be queued for one lead at once, just not two of the same provider. A single `EnrichmentWorker` background thread in the daemon process **always runs** (no longer flag-gated), claims `enrich_phone` and `enrich_email` tasks (the outbound loop excludes both, and also excludes `gmail_follow_up`), and routes phone payloads on the `provider` field: `"waterfall"` first returns any cached `Lead.phones` entry from the provider chain, otherwise runs only untried providers in failover order — BetterContact → LeadMagic → Prospeo (`linkedin/enrichment/waterfall.py`), stopping on the first `FOUND`/`NOT_FOUND` and escalating only on `API_FAILURE`; a specific provider name (looked up in `PROVIDERS_BY_NAME`) first returns any existing `Lead.phones` entry for that provider, otherwise runs that provider only with no failover. Provider HTTP uses certifi's CA bundle so daemon hosts with stale system trust stores can still call enrichment APIs reliably, and provider `API_FAILURE` results persist structured status/body details in `Task.error` for triage and post a cooldown-gated ops Slack degraded alert keyed by provider/reason/status. **Multi-number**: a lead carries many numbers — `Lead.phones` is a JSON list of `{number, provider, found_at}` (one entry per provider that hit; `Lead.phone_numbers` is the bare-string convenience view). `Lead.phone_providers_tried` records every phone provider that gave a *definitive* answer (`FOUND` or `NOT_FOUND`); a cached provider-specific phone lookup also stamps that provider as tried before notifying Slack. `Lead.email_providers_tried` does the same for email providers. `API_FAILURE` is not recorded, so it stays retryable. Worker is HTTP-only (no browser), so it is not gated on active hours; stale `RUNNING` enrichment tasks are reclaimed on `start()` (the daemon has no clean shutdown). Providers implement the `PhoneProvider` protocol in `linkedin/enrichment/base.py` — adding one is a new file plus one line in `PROVIDER_CHAIN`.

Reply-draft generation uses a 12-message recent thread window and is prompted to warm up the conversation, clarify the ask, and avoid pitching Boundera unless the prospect explicitly needs product context.

- **Node monitoring**: `linkedin/monitoring/` — peer-node liveness + sender activity health + in-daemon task-failure detection, no third-party service. Each daemon is a "node"; gated by `ENABLE_NODE_MONITOR` (default on). A `NodeMonitor` background thread (`node_monitor.py`, same pattern as `EnrichmentWorker`) stamps this node's `crm`-adjacent `DaemonHeartbeat` row (`linkedin` app — one row per sender, keyed by resolved operator handle) every `MONITOR_INTERVAL_SECONDS` and scans peers' rows; only senders whose `LinkedInProfile.active` DB switch is enabled are monitored, and a monitored peer whose `last_alive` is older than `PEER_STALE_MINUTES` is reported down to the **ops Slack channel** via `notify_degraded`. Disable an intentionally retired sender in Django Admin by clearing its LinkedIn profile's `active` checkbox; its historical heartbeat row can remain without producing alerts. `down_alerted_at` is an atomic claim+cooldown marker — exactly one peer posts per outage, re-claimable only after `DEGRADED_REALERT_HOURS`. `last_alive=NULL` means intentionally stopped (the daemon calls `clear_heartbeat` on a clean empty-queue exit so peers don't false-alarm). The same monitor thread runs `check_expected_sender_activity`: expected senders (from `EXPECTED_OUTBOUND_SENDERS`, or inferred from active profiles with active campaigns) must show outbound `ActionLog` progress after `SENDER_ACTIVITY_GRACE_MINUTES`; fresh heartbeat + stale due outbound work with no recent action for `SENDER_ACTIVITY_STALE_MINUTES` alerts as "outbound activity looks stuck". Before declaring a sender stuck, it checks `LinkedInProfile.can_execute()` for due action types; a sender blocked by daily/weekly limits alerts as "hit a rate limit" instead. `activity_alerted_at` is the cooldown marker for both activity-stuck and activity-limit alerts; healthy observations do not clear it because peer daemons may use different runtime rate-limit overrides, so repeat activity alerts remain suppressed for the full `DEGRADED_REALERT_HOURS`. Degraded detection inside the daemon is now only `TaskFailureTracker` (in-process consecutive-failure counter wired into the dispatch loop — `TASK_FAILURE_STREAK_THRESHOLD` failures in a row → alert). Listener heartbeat files are still used for listener catch-up, but there is no self-alerting "realtime listener looks stuck" check. The thread runs through off-hours sleeps; monitoring failures are logged and never crash the daemon.
