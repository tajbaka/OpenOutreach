# AGENTS.md

## Rules

- **Python env**: Always use `.venv/bin/python` (not system `python3`).
- **Commits**: No `Co-Authored-By` lines. Single-line messages (no body).
- **Dependencies**: Managed in `requirements/*.txt` (used by local dev and Docker).
- **Docs sync**: When modifying code, update AGENTS.md and ARCHITECTURE.md to reflect changes.
- **No memory**: Never use the auto-memory system (no MEMORY.md, no memory files). All persistent context belongs in AGENTS.md or ARCHITECTURE.md.
- **Error handling**: App should crash on unexpected errors. `try/except` only for expected, recoverable errors. Custom exceptions in `exceptions.py`.
- **No backward compat**: CRM models are owned by this project — no need for backward compatibility shims, legacy migration code, or re-export modules. Simplify freely.

## Project Overview

OpenOutreach — self-hosted LinkedIn automation for B2B lead generation. Playwright + stealth for browser automation, LinkedIn Voyager API for profile data, Django + Django Admin for CRM (models owned by this project).

`import_connections` reads a CSV with either of these header sets:
- `LinkedIn URL, First Name, Message` (manual outreach log; `Message` becomes the seeded outbound `crm.Message`)
- `Profile URL, First Name, Last Name, Company` (standard LinkedIn-Connections export; no outbound message column)

The parser auto-detects which format and treats `Message` / `Last Name` / `Company` as optional bonuses. It logs into LinkedIn using `BACKFILL_LINKEDIN_USERNAME`/`BACKFILL_LINKEDIN_PASSWORD` from `.env`, scrapes the Connections page back N days, and creates Lead+Deal rows at `state=CONNECTED` for each row also present in the scraped connections. The SKIP path (lead already at CONNECTED+) backfills `Deal.connected_at` from the scrape's `connected_on` date if it was null. Skips URLs that already have a Deal in any non-backfill campaign so the daemon's outreach state is never disturbed. Outbound messages from the CSV are persisted to `crm.Message` with `external_id="csv:<path>:<url>"`; inbound messages flow through `get_conversation`'s persist hook. `sync_sheets` mirrors these to Google Sheets on its next hourly run — this command never touches Sheets directly.

`discover_inbox_leads` crawls LinkedIn Messaging conversations via the Voyager Messaging inbox API, not the Connections page. After login it first opens the visible browser tab to `/messaging/` and pauses briefly, then reads the same authenticated Messaging GraphQL endpoints from that browser context. The first inbox batch uses LinkedIn's recent-conversation query; older batches use the same `lastUpdatedBefore` / `nextCursor` category query the UI emits when the conversation list is scrolled, stopping at `--since-days` (default 90) or `--max-pages`. It skips existing CRM Leads by canonical LinkedIn URL, `Lead.public_identifier`, stored profile URN, and any thread already present in `crm.Message.thread_external_id`. It resolves/enriches the other 1:1 participant profile when LinkedIn allows it; if Voyager blocks the full profile, it falls back to the inbox participant payload (name, headline, profile URL / `fsd_profile` URN) so private/restricted inbox senders can still be reviewed without breaking duplicate checks. It fetches the thread, then asks a Boundera FedRAMP/CMMC LLM prompt (`inbox_lead_relevance.j2`, using `LLM_API_KEY` / `AI_MODEL`) whether the profile plus conversation is relevant and which canonical `Lead.icp` bucket it belongs to (`CSPs`, `3PAOs/Assessors`, `Advisors`, `Channel`, `CMMC Buyers`, `CMMC Advisor/Channel`). The selected Campaign is only the destination Deal campaign; stale Campaign objective/docs are not used for inbox discovery relevance. With `--apply`, qualified discoveries are inserted as `Lead` plus `Deal(state=CONNECTED)`, `Lead.icp` is stamped from the classifier, and their thread is persisted through `linkedin.db.messages.persist_thread`; `Deal.last_reply_at` is stamped from the newest inbound message. Because it creates Deals at `CONNECTED` and leaves `Lead.disqualified=False`, `sync_sheets` will mirror them to the People tab on the next run. It never creates `Task` rows, so follow-up automation only sees these records if a separate workflow later chooses to act on them.

## Architecture (quick reference)

For detailed module docs, see `ARCHITECTURE.md`.

- **Entry**: `manage.py` — no args runs daemon (startup checks → onboarding → browser → task queue loop); with args delegates to Django CLI. Auto-migrates + CRM bootstrap on startup. Startup integrity checks run first in the no-args branch, before migrations: `linkedin/version_check.py:check_for_updates()` compares the checkout against its git upstream (`@{u}`) and, when behind, prompts on a TTY or auto-pulls headless. A successful `git pull --ff-only` exits 0 so the process can restart on fresh code; a failed pull exits 1 after `notify_error`. It is a silent no-op when there is no `.git` checkout. `linkedin/env_check.py:check_env_vars()` then logs one grouped advisory warning for missing env vars declared in `linkedin/env_spec.py`, which is the canonical env-var registry.
- **State machine**: `enums.py:ProfileState` — QUALIFIED → READY_TO_CONNECT → PENDING → CONNECTED → COMPLETED / FAILED. Deal.state is a CharField with ProfileState choices (no Stage model). `ClosingReason` (COMPLETED/FAILED/DISQUALIFIED) on Deal.closing_reason. `Lead.disqualified=True` = permanent exclusion. LLM rejections = FAILED Deals with DISQUALIFIED closing reason (campaign-scoped). `Deal.connected_at` is stamped once when `set_profile_state` flips into CONNECTED — stable timestamp the daemon's rigid follow-up handler (`linkedin/tasks/follow_up.py`) uses for connected-no-reply cohort tracking.
- **Task queue**: `Task` model (persistent). Types: `connect`, `follow_up`, `sweep_connections`, `status_summary`, `enrich_phone`, `enrich_email`, `gmail_follow_up`, `manual_reply`. Handlers in `linkedin/tasks/`, signature: `handle_*(task, session, qualifiers)` for LinkedIn/browser tasks; Gmail post-accept cadence code lives in the top-level `gmail` package. `Task.objects.claim_next()` atomically flips the returned task from `pending` to `running`; this is part of the cancel-safety contract for manual replies, so callers must treat a returned task as already claimed. `manual_reply` is the Slack-to-LinkedIn reply lane: Slack modal submit inserts a pending task with `lead_id`, `operator`, `message`, and Slack message metadata; the queued Slack status includes a cancel button that deletes the task only while it is still `pending`. The daemon claims matching-operator manual replies ahead of normal outbound work, sends them through the same logged-in Playwright page, bypasses active-hours sleeps when due, and leaves quotas, sequences, and Deal state untouched. Manual replies use direct-thread UI typing and disable the Voyager API fallback, so a UI send failure fails the task instead of sending instantly. Manual reply sends persist outbound `crm.Message` rows under `manual-reply:` synthetic external ids; the handler checks that same ledger for an existing same lead/operator/body manual reply before sending, so crash retries do not double-send. Slack sent/failed acknowledgements are best-effort via `chat.update` on the original notification, falling back to the interaction `response_url`. `sweep_connections` replaces the legacy per-profile `check_pending` — one visit to `mynetwork/invite-connect/connections/` every `CONNECTION_SWEEP_INTERVAL_HOURS` cross-references accepted invitations in bulk. Plain accepted invites are not posted individually to Slack, and sweep completion no longer posts send-count status. Independently gated by `ENABLE_SWEEP_CONNECTIONS`; the post-accept follow-up DM is gated separately by `ENABLE_FOLLOW_UP`, so you can detect accepts (and mirror to Sheets) without auto-DMing. `status_summary` is an account-agnostic hourly task: whichever daemon claims it posts one all-sender ops Slack snapshot, with per-sender counts for invites, LinkedIn follow-ups, email follow-ups, manual replies, newly accepted since the previous status window, connect tasks run today, and qualified remaining, then queues the next run one hour later. It is seeded on daemon startup and allowed through active-hours sleeps like manual replies. `follow_up` payloads may carry `sequence_name`, `channel`, and `step_index`; missing fields default to the current one-step `linkedin_connect_followup` / same channel / `0` behavior. Non-final follow-up steps enqueue the next step after that step's `delay_hours`, calculated from `Deal.connected_at` and normalized into configured active hours/rest days; step-level dedup for a non-final already-sent step keeps the Deal `CONNECTED` and ensures the next step is queued; post-send DB retry only retries the state write, not `ActionLog` or next-step enqueue. Gmail sequencing is scheduled from post-accept paths through `gmail.handoff.maybe_schedule_gmail_sequence`; when `ENABLE_GMAIL_SEQUENCE=false` it no-ops, and when enabled it queues either `enrich_email` or `gmail_follow_up` without putting Gmail send logic inside the LinkedIn handler. The first Gmail task is connection-anchored, but later Gmail steps are scheduled from the previous Gmail send time so catch-up runs cannot compress the sequence. Gmail template routing uses `resolve_icp(lead)`, so stamped `Lead.icp` buckets such as `Channel`, `CMMC Buyers`, and `CMMC Advisor/Channel` are honored before legacy classifier backfill. LinkedIn and Gmail are fail-open lanes: Gmail scheduling exceptions are logged and swallowed at the LinkedIn boundary, and templates must be standalone rather than referencing a previous channel-specific send. The main LinkedIn outbound loop excludes `enrich_phone`, `enrich_email`, and `gmail_follow_up`; a separate browserless `gmail.worker.GmailWorker` claims only `gmail_follow_up` tasks whose `payload.operator` matches the daemon's resolved operator. Gmail API auth/client/worker/task handlers and email copy live under `gmail/`; Gmail sequence copy is `gmail/icp_emails.json`, separate from LinkedIn's `linkedin/icp_messages.json`. Gmail auth maps Arian/Leili to `arian_boundera` and Athena/Eddy/Chuka to `eddy_boundera`; Chuka sends as `eddy@getboundera.com` while Gmail templates render `{my_name}` as `Eddy`. Gmail OAuth tokens request send, compose/draft, settings, and readonly scopes. Missing Gmail copy for a sender/ICP/step is treated as that lane being disabled for the lead and skips cleanly; malformed template rows still fail loudly. Gmail subjects/bodies are parsed against an explicit placeholder allowlist (`first_name`, `last_name`, `company_name`, `my_name`, `our_company_name`, `our_website_url`) before rendering, `company_name` uses the same safe `Unknown Company` fallback as LinkedIn copy, and `manage.py validate_gmail_templates` renders every checked-in Gmail step with a fake lead as a pre-send guard. Blank email subject/body cells in the ICP Messages Sheet pull path save that sender/ICP Gmail block as an empty list, so cleared Sheet copy disables stale JSON sends. LinkedIn send history and dedupe remain `crm.Message`-based: synthetic daemon sends use `external_id` values under `daemon-send:`, and cross-campaign dedupe still keys on `Message.sender` canonicalized via `resolve_operator` rather than parsing `external_id`; add every LinkedIn sender display variant to `linkedin/operators.py` (including display names like `"athena aghdami"`) or legitimate follow-ups will be owner-guard skipped.
- **Task type validation**: `Task.task_type` keeps the `Task.TaskType` enum choices, but `Task.save()` skips task-type choice validation so unknown or newly deployed task rows can still be marked failed instead of validation-crashing startup during deploy skew.
- **Sweep ownership**: `sweep_connections` is a sender-scoped DB task (`payload.operator`). Each sender daemon claims only its own sweep row, checks acceptances for that logged-in LinkedIn account's campaigns, and computes post-accept follow-up delays with `ActionLog.ActionType.FOLLOW_UP`; do not create unscoped `{}` sweep tasks.
- **Status summary metrics**: Hourly Slack status summaries separate LinkedIn follow-ups (`ActionLog` follow_up rows) from email follow-ups (outbound Gmail `crm.Message` rows with `gmail-send:<operator>:` external ids). A sender is omitted from the hourly summary once it has no heartbeat for the active day or its connect lane has hit the daily/weekly limit; when all rows are omitted, the task silently reschedules without posting Slack. The entire Slack post is also suppressed during intentional quiet windows: outside active hours/rest days and no pacing catch-up lane open for any sender.
- **Manual reply latency**: The daemon caps idle sleeps to `MANUAL_REPLY_POLL_SECONDS` whenever manual replies are claimable, including active hours, so Slack-queued replies are picked up quickly even if the next normal outbound task is far in the future.
- **ML pipeline**: GPR (sklearn) + BALD active learning + LLM qualification. Per-campaign models stored in `Campaign.model_blob` (DB).
- **Config**: `.env` / `.env.example` (the declared project-owned vars in `linkedin/env_spec.py`; `.env.example` should stay in registry order), `conf.py:CAMPAIGN_CONFIG` (timing/ML defaults), `conf.py` browser constants (`BROWSER_*`, `HUMAN_TYPE_*`, `VOYAGER_REQUEST_TIMEOUT_MS`), `conf.py` schedule constants (`ENABLE_ACTIVE_HOURS` flag, active hours/timezone/rest days), `conf.py` realtime constants (`ENABLE_REALTIME_LISTENER` flag, `LISTENER_CDP_PORT`, `LISTENER_CATCHUP_GAP_MINUTES`, `LISTENER_PUMP_SLICE_SECONDS`, listener-specific active hours/rest days), `conf.py` feed-collection constants (`ENABLE_LINKEDIN_FEED_COLLECTOR`, daily collection time/timezone, retry minutes, max posts, stop-after-seen, scroll pause), `conf.py` enrichment/Gmail cadence constants (`ENABLE_GMAIL_SEQUENCE`, `ENABLE_AUTO_PHONE_ENRICHMENT`, `ENRICHMENT_MAX_DURATION_SECONDS`, `ENRICHMENT_HTTP_TIMEOUT_SECONDS`, `BETTERCONTACT_POLL_INTERVAL_SECONDS`, `BETTERCONTACT_API_KEY`, `LEADMAGIC_API_KEY`, `PROSPEO_API_KEY`), `conf.py` Slack action constants (`MANUAL_REPLY_POLL_SECONDS`), `conf.py` node-monitoring constants (`ENABLE_NODE_MONITOR` flag, `MONITOR_INTERVAL_SECONDS`, `PEER_STALE_MINUTES`, `DEGRADED_REALERT_HOURS`, `TASK_FAILURE_STREAK_THRESHOLD`, `EXPECTED_OUTBOUND_SENDERS`, `SENDER_ACTIVITY_GRACE_MINUTES`, `SENDER_ACTIVITY_STALE_MINUTES`), Vercel function env (`SLACK_SIGNING_SECRET`, `SLACK_BOT_TOKEN`, `DATABASE_URL`, `LLM_API_KEY`, `AI_MODEL`, optional `LLM_API_BASE` — set on the Vercel project; bot token is needed for reply/context modals and message updates, LLM env is needed for lead-context AI summary and reply-modal draft generation), `conf.py` onboarding defaults (`DEFAULT_*_LIMIT`), Campaign/LinkedInProfile models (Django Admin).
- **Database**: Postgres from `DATABASE_URL` is required for every non-test runtime; tests use in-memory SQLite. Neon is the current managed default, but self-hosted shared Postgres is supported by the same `DATABASE_URL` contract. Daemon machine + dev box MUST share one database URL to avoid split-brain (lesson from 2026-04-26 cutover). Use `docs/self-hosted-postgres.md` + `make selfhost-db-*` to test a local Docker Postgres copy before any cutover. Deps: `dj-database-url`, `psycopg[binary]>=3.1`.
- **Sheets sync**: standalone `manage.py sync_sheets` (gspread + service-account auth). Iterates Deals at `state >= PENDING` and **disqualified=False**, groups by `company_name`, and writes one row per Lead into a single People tab keyed by LinkedIn URL. 15 columns: Name, First name, Last name, Company, Title, LinkedIn URL, Email addresses, Outreach status, Stage, Priority, Primary location, Notes, AI Notes, Created at, Last synced. The Stage column is the company-level aggregate (`aggregate_company_stage`: Won wins; furthest-along active stage; all-Lost → Lost) denormalized onto each row. Per-lead derivation (`deal_to_stage` / `deal_to_outreach_status`): PENDING→Prospecting/Invite Sent, CONNECTED-no-reply→Prospecting/Connected, CONNECTED+last_reply_at→Qualification/Replied, FAILED→Lost. **`COMPLETED` is the daemon's automation-finished state (invite accepted + rigid follow-up DM sent), not a closed-won deal** — it derives from engagement signal: a `crm.Meeting` exists→Meeting/Had Meeting, else `last_reply_at` set→Qualification/Replied, else→Prospecting/Connected. The auto-mapping **never produces Won** — `Won`/`Stage-Won` are human-set sales outcomes only. Stage hierarchy: Prospecting → Qualification → Meeting → Closing → Won (Lost terminates). Meeting and Closing are also human-driven; `should_patch_stage` prevents downgrades. **Outreach status rank**: Invite Sent → Connected → Waiting → Replied → Wants Meeting → Meeting Booked → Had Meeting → Manual followup → Prospecting to close → Won → Don't send (Lost is terminal-negative, separately overridable). `should_patch_outreach_status` blocks demotion so manual sheet edits are never clobbered. **Priority** defaults to "Low" when empty so the column never has blanks. The Lead model has no per-row sheet pointer — `LinkedIn URL` is the natural key, and `SheetIndex.load()` slurps the whole tab in one API call per sync run. Decoupled from the daemon — failures don't affect outreach. Module: `linkedin/notifications/sheets.py`.
- **Followup sheet workflow**: `docs/followup-generation-workflow.md` is the human-run Claude workflow that writes `<Operator> - Followups` tabs. Phase 1 separates ball-on-court cohort from time-gap posture by stamping `conversation_freshness` / `draft_posture`; Phase 5 must obey that posture so stale/cold threads reopen naturally and archival threads are held unless there is a fresh reason to write.
- **Synthesis pass (Phase D)**: `sync_sheets`'s per-Lead loop runs `linkedin.notifications.synthesis.synthesize_for_deal(deal, current_outreach_status=...)` between reading the existing sheet row and writing the new one. **D1**: regex-extracts an email from inbound `crm.Message` rows and writes it to `Lead.email`; sync_sheets folds the union of Lead.email + existing sheet emails into the row payload. **D2**: runs a cheap LLM (`AI_MODEL`) over the thread; returns a `SynthResult(wants_meeting_now, note_block)` that sync_sheets folds into the row's Outreach status + Notes columns. Gated by `Deal.wants_meeting_detected_at` (lock-in), `Deal.last_synthesized_at` vs latest `Message.sent_at` (skip when no new signal), and current sheet status rank ≥ Wants Meeting (skip when human already advanced past it). Synthesis failures are logged and never block the sync.
- **Message store**: `crm.Message` (FK to Lead, source enum {linkedin/gmail/calendar}, direction {inbound/outbound}, idempotent on `(source, external_id)`). Populated as a side effect of `linkedin.actions.conversations.get_conversation()` — every existing caller (sweep_connections, follow_up, agent) auto-persists threads via `linkedin.db.messages.persist_thread`. LinkedIn direction inference normalizes sender names and strips common honorifics (for example `Dr.`) before comparing to the Lead name, while explicit daemon operator senders still force outbound; LinkedIn invite-note echoes that arrive with the lead as sender are also forced outbound when they match stored `sent_note` text or a narrow legacy connect-note pattern. `linkedin.actions.message.send_raw_message` / `send_media_message` persist successful daemon sends via `linkedin.db.chat.save_chat_message`; sequence-aware follow-up sends use `daemon-send:<operator>:<deal_id>:<sequence_name>:step-<index>:<timestamp>`, while older/manual daemon sends may still use `daemon-send:<lead_id>:<timestamp>`. `import_connections` and `discover_inbox_leads` also seed LinkedIn messages outside the daemon path; the inbox importer creates the Lead first, then writes the thread via `persist_thread` with the logged-in sender passed as an explicit outbound sender. Gmail threads land via `linkedin.notifications.gmail_threads.persist_gmail_threads` — the data-sync workflow (`docs/data-sync-workflow.md` Phase 0) hands MCP-fetched thread payloads to it; direction is inferred against a `self_emails` set the caller resolves at run start (primary mailbox + Send-As aliases from Gmail Profile API). The same module's `classify_ball_on_court(lead)` reads the merged LinkedIn+Gmail timeline so an email reply correctly flips a LinkedIn-silent lead to "ball on us".
- **Realtime listener**: `linkedin/realtime/` — near-realtime inbound LinkedIn DM detection, gated by `ENABLE_REALTIME_LISTENER` (`conf.py`, default off). Runs as a **separate child process** (`manage.py listen_realtime`) that the daemon spawns and supervises (`linkedin/realtime/supervisor.py` — restart on death, give up after 5 spawn failures, run/stop on listener-specific hours). Listener schedule is independent from outbound automation: `LISTENER_ACTIVE_START_HOUR=0`, `LISTENER_ACTIVE_END_HOUR=24`, `LISTENER_REST_DAYS=` by default, so inbound notifications can stay on while connect/follow-up automation sleeps. The daemon launches Chromium as a *persistent context* (`data/profile-<account>/`) with a fixed `--remote-debugging-port` (`LISTENER_CDP_PORT`); the listener `connect_over_cdp`s to that same browser, shares its one context (one device, one cookie jar), opens a `/messaging/` tab, and streams LinkedIn's realtime feed via CDP `streamResourceContent` → `sse.py` (SSE framing) → `parser.py` → `handler.py` (resolve `Lead`, persist `crm.Message`, Slack-notify inbound via `notify_message_received`). Reply Slack notifications include the full Slack-safe quoted message body, preserving line breaks and only truncating near Slack's 3000-character section limit, and carry the triggering LinkedIn `thread_external_id` so the manual-reply modal can show the right sender-specific thread when one Lead is shared across operators. Slack HTTP posts use certifi's CA bundle so daemon hosts with stale system trust stores still notify reliably. Separate processes = separate Playwright loops, which is why this works where the in-process v1 design did not. The listener reconnects on a dropped CDP connection; heartbeat at `data/listener-heartbeat-<account>.json`; startup catch-up (`catchup.py`) surfaces the listener-offline gap and prompts for backfill on a TTY, but the prompt defaults to no after 10 seconds so startup cannot hang unattended. Realtime is an enhancement — any failure degrades to the existing polling. (`StandaloneLinkedInSession` for backfill/sales-nav stays on the legacy JSON cookie jar — only the daemon uses a persistent context.)
- **LinkedIn feed collector/analyzer**: collector browser path plus Codex-reviewed saved-post analyzer. When `ENABLE_LINKEDIN_FEED_COLLECTOR=true`, `daemon_supervisor.py` wakes a nonblocking child process once daily at `LINKEDIN_FEED_COLLECTION_HOUR:LINKEDIN_FEED_COLLECTION_MINUTE` in `LINKEDIN_FEED_COLLECTION_TIMEZONE` (default 17:00 America/Toronto): `.venv/bin/python manage.py collect_linkedin_feed`. The command resolves the same daemon account as outbound automation, claims/creates a `LinkedInFeedCollectionJob`, connects over CDP to the daemon's persistent Chromium (`LISTENER_CDP_PORT`), opens its own `/feed/` tab, parses LinkedIn relative timestamps, and stops once it reaches the previous sender collection window plus `LINKEDIN_FEED_COLLECTION_CUTOFF_OVERLAP_MINUTES` (default 1 minute). It stores canonical `LinkedInFeedPost` rows plus per-sender `LinkedInFeedObservation` rows; post links prefer exact feed/update or post permalinks, fall back to an activity-URN feed-update URL when available, and keep raw candidate anchors for diagnostics. `LINKEDIN_FEED_COLLECTION_MAX_POSTS` and `LINKEDIN_FEED_COLLECTION_STOP_AFTER_SEEN` remain safety caps for unparseable/non-chronological feed items. Failed jobs are marked `failed` and rescheduled after `LINKEDIN_FEED_COLLECTION_RETRY_MINUTES`; completed jobs create the next day's row. `manage.py analyze_linkedin_feed` does not call an LLM; it exports a JSON queue for Codex daily automation and applies Codex-produced decisions, persisting intent/audience/topics/reason/suggested action on `LinkedInFeedPost` and posting high/urgent FedRAMP/CMMC/GRC/advisor/partner hits to `SLACK_HIGH_SIGNAL_URL`.
- **Phone/email enrichment / Slack actions**: `linkedin/enrichment/` plus `api/slack_enrich.py` — phone enrichment is **operator-triggered from Slack**. Every inbound-reply Slack notification carries a "📞 Get phone number" select menu (waterfall / bettercontact / leadmagic / prospeo), a "Reply on LinkedIn" button, and a "Lead context" button. The operator's pick/button/modal submit is POSTed by Slack to the Vercel serverless function, which verifies the Slack request signature (`SLACK_SIGNING_SECRET`, HMAC-SHA256) and routes requests through an explicit action-id-to-handler dispatch table rather than a growing conditional chain. Phone enrichment picks INSERT an `enrich_phone` Task; reply modal submits INSERT a daemon-dispatched `manual_reply` Task with original Slack blocks so the daemon can later update the notification. The reply modal fetches the recent LinkedIn `crm.Message` thread via raw SQL and renders a compact transcript above the reply textbox; it also has a bottom-left "Draft reply" action that calls the configured OpenAI-compatible LLM endpoint (`LLM_API_KEY`, `AI_MODEL`, optional `LLM_API_BASE`) and fills the reply textbox with the suggested LinkedIn reply. New reply/context buttons carry the triggering `thread_external_id`, so shared Lead rows across multiple senders do not mix transcripts, while legacy buttons fall back to the latest inbound LinkedIn thread for that lead. The Lead context modal fetches deterministic Lead/Deal/profile/thread context via raw SQL and can update the modal with an AI summary; generated summary/draft artifacts are saved to `linkedin.SlackLeadContextArtifact`, scoped by `(lead, operator, thread_external_id, kind)`, so reopening context/reply flows can reuse sender-specific sections. Slack `private_metadata` is only an open-modal cache while another action runs; if it grows too large, reply-modal thread preview blocks are dropped before original source-message blocks so queued/cancel/sent status updates still have the original Slack message to update. Loading rows and generated sections render at the bottom of the active modal so the operator watches progress and result appear below existing context. If best-effort context/preview fetch fails, the reply modal still opens. Email enrichment is **not** Slack-triggered: when post-accept Gmail is enabled, post-accept Gmail scheduling queues `enrich_email` for leads without `Lead.email`. `enrich_email` uses BetterContact in email-only mode (`enrich_email_address=true`, `enrich_phone_number=false`), writes found addresses to `Lead.email`, records definitive BetterContact answers in `Lead.email_providers_tried`, and then queues `gmail_follow_up` step 0. The function uses raw `psycopg` (no Django import), and `SLACK_BOT_TOKEN` is required for `views.open`/`views.update`; queued status updates prefer the interaction `response_url` and only fall back to `chat.update` when metadata is available, while sent/failed status uses daemon-side `chat.update` and falls back to `response_url`. The `Task` table is the entire contract between the function and the daemon. The function re-posts the notification with the **select menu kept live** (`render_response_blocks`) so the operator can run several providers on one lead from the same message; a status line accumulates the requested providers (its `block_id` carries the set across picks). The realtime listener can *also* auto-enqueue a `waterfall` task on every inbound reply, gated by `ENABLE_AUTO_PHONE_ENRICHMENT` (default off). Phone enrichment paths dedup per `(lead, provider)` against an existing pending/running task — so BetterContact and LeadMagic can be queued for one lead at once, just not two of the same provider. A single `EnrichmentWorker` background thread in the daemon process **always runs** (no longer flag-gated), claims `enrich_phone` and `enrich_email` tasks (the outbound loop excludes both, and also excludes `gmail_follow_up`), and routes phone payloads on the `provider` field: `"waterfall"` first returns any cached `Lead.phones` entry from the provider chain, otherwise runs only untried providers in failover order — BetterContact → LeadMagic → Prospeo (`linkedin/enrichment/waterfall.py`), stopping on the first `FOUND`/`NOT_FOUND` and escalating only on `API_FAILURE`; a specific provider name (looked up in `PROVIDERS_BY_NAME`) first returns any existing `Lead.phones` entry for that provider, otherwise runs that provider only with no failover. Provider HTTP uses certifi's CA bundle so daemon hosts with stale system trust stores can still call enrichment APIs reliably, and provider `API_FAILURE` results persist structured status/body details in `Task.error` for triage and post a cooldown-gated ops Slack degraded alert keyed by provider/reason/status. **Multi-number**: a lead carries many numbers — `Lead.phones` is a JSON list of `{number, provider, found_at}` (one entry per provider that hit; `Lead.phone_numbers` is the bare-string convenience view). `Lead.phone_providers_tried` records every phone provider that gave a *definitive* answer (`FOUND` or `NOT_FOUND`); a cached provider-specific phone lookup also stamps that provider as tried before notifying Slack. `Lead.email_providers_tried` does the same for email providers. `API_FAILURE` is not recorded, so it stays retryable. Worker is HTTP-only (no browser), so it is not gated on active hours; stale `RUNNING` enrichment tasks are reclaimed on `start()` (the daemon has no clean shutdown). Providers implement the `PhoneProvider` protocol in `linkedin/enrichment/base.py` — adding one is a new file plus one line in `PROVIDER_CHAIN`.
- **Manual reply diagnostics / drafting**: Manual replies pass `raise_on_failure=True` into the LinkedIn UI send path so task failures include the concrete send reason and the daemon diagnostics folder path in `Task.error`. Reply-draft generation uses a 12-message recent thread window and is prompted to warm up the conversation, clarify the ask, and avoid pitching Boundera unless the prospect explicitly needs product context.
- **Rigid ICP outbound templates**: `linkedin/icp_messages.json` holds rigid outbound messages. Current legacy channel shape is `{sender: {icp: {channel: [variants]}}}`; follow-up channels can also use the sequence shape `{channel: [{"delay_hours": 0, "variants": [...]}, {"delay_hours": 96, "variants": [...]}]}`. Fractional `delay_hours` values are valid, so Gmail can use `0.33` for a roughly 20-minute same-day touch. ICP blocks can declare `"media": ["demo.gif"]`; templates in that ICP can then reference `{demo.gif}` to attach the file, resolved from `assets/follow_up/` or `assets/followup/`. The legacy `{add demo.gif}` attachment syntax still works. `icp_outbound.channel_steps()` normalizes both shapes, preserving lead-id variant rotation inside each step. Sequenced follow-up channels round-trip through Sheets: `sync_icp_messages --push` renders interleaved dynamic `Followup Message N`, `Email Subject N`, and `Email Body N` columns, and `--pull` rebuilds the sequence from those columns. Default post-accept cadence is LinkedIn at Day 0, Gmail at +0.33 hours, LinkedIn at Day 4, and Gmail at Day 8 — `save_icp_messages` preserves the existing per-step `delay_hours` (the Sheet carries copy, not cadence), preserves non-sheet fields like `media`, and never flattens a real multi-step sequence when the extra columns are left blank. The editable ICP Messages tabs include `CSPs`, `3PAOs/Assessors`, `Advisors`, `Channel`, `CMMC Buyers`, and `CMMC Advisor/Channel` so partner/agency-routing and CMMC-specific copy can be reviewed in Sheets before being pulled into JSON. The top level is keyed by the sending operator's canonical handle (`linkedin.operators.resolve_operator`, e.g. `Arian` / `Chuka` / `Athena` / `Leili`) so each sender can ship different copy; under each sender, one entry per ICP × channel. There is **no shared default sender** — a sender absent from the JSON raises `SheetsError` (no-silent-fallback rule) rather than borrowing another operator's copy. Used by the daemon's `handle_follow_up` task (and `build_connection_note` in the connect lane) to DM leads programmatically — high-volume blast with no LLM personalization, only mechanical `{first_name}` / `{company_name}` / `{our_company_name}` / `{our_website_url}` / `{my_name}` substitutions. The filler treats `"Unknown Company"` and similar sentinels as missing data and renders `{company_name}` as `"your team"` so placeholders never leak into outreach; Slack reply notifications hide the sentinel company line. Loader / filler: `linkedin/icp_outbound.py` — `load_icp_messages(sender)`, `channel_steps(sender=..., ...)`, `fill_message(sender=..., ...)`, `fill_for_lead(sender=..., ...)` all take the sender; callers pass `resolve_operator(session.linkedin_profile.linkedin_username)`. **Onboarding a new sender** = add a block under their handle here, and (ideally) an alias in `linkedin/operators.py`. The daemon's startup check (`manage.py:_verify_sender_templates`, via `icp_outbound.missing_sender_block`) hard-fails if the account it runs as has no block, and warns for any other active account that lacks one. Companion to the Sheets `ICP Goals` tab which carries the per-ICP strategic goal used by the Codex-run followup workflow for warm cohorts (Met / ball-on-us). ROLE→ICP routing reuses `FU_ROLE_TO_ICP`.
- **Node monitoring**: `linkedin/monitoring/` — peer-node liveness + sender activity health + in-daemon task-failure detection, no third-party service. Each daemon is a "node"; gated by `ENABLE_NODE_MONITOR` (default on). A `NodeMonitor` background thread (`node_monitor.py`, same pattern as `EnrichmentWorker`) stamps this node's `crm`-adjacent `DaemonHeartbeat` row (`linkedin` app — one row per sender, keyed by resolved operator handle) every `MONITOR_INTERVAL_SECONDS` and scans peers' rows; a peer whose `last_alive` is older than `PEER_STALE_MINUTES` is reported down to the **ops Slack channel** via `notify_degraded`. `down_alerted_at` is an atomic claim+cooldown marker — exactly one peer posts per outage, re-claimable only after `DEGRADED_REALERT_HOURS`. `last_alive=NULL` means intentionally stopped (the daemon calls `clear_heartbeat` on a clean empty-queue exit so peers don't false-alarm). The same monitor thread runs `check_expected_sender_activity`: expected senders (from `EXPECTED_OUTBOUND_SENDERS`, or inferred from active profiles with active campaigns) must show outbound `ActionLog` progress after `SENDER_ACTIVITY_GRACE_MINUTES`; fresh heartbeat + stale due outbound work with no recent action for `SENDER_ACTIVITY_STALE_MINUTES` alerts as "outbound activity looks stuck". Before declaring a sender stuck, it checks `LinkedInProfile.can_execute()` for due action types; a sender blocked by daily/weekly limits alerts as "hit a rate limit" instead. `activity_alerted_at` is the cooldown marker for both activity-stuck and activity-limit alerts. Degraded detection inside the daemon is now only `TaskFailureTracker` (in-process consecutive-failure counter wired into the dispatch loop — `TASK_FAILURE_STREAK_THRESHOLD` failures in a row → alert). Listener heartbeat files are still used for listener catch-up, but there is no self-alerting "realtime listener looks stuck" check. The thread runs through off-hours sleeps; monitoring failures are logged and never crash the daemon.
